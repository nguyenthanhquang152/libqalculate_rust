# Porting Guidelines: C++ to Rust Coding Conventions

These guidelines define how agents must port `libqalculate` 5.11.0 into Rust while
preserving user-visible behavior. The upstream checkout at `../libqalculate` is the
reference implementation and must not be edited unless the user explicitly asks.

The port should be idiomatic Rust, but compatibility wins over internal similarity. When
Rust internals intentionally differ from C++, document the preserved behavior and add oracle
tests.

## 1. Unsafe Rust Policy

Unsafe Rust is forbidden by default.

- Pure Rust modules must use `#![forbid(unsafe_code)]` or inherit a crate-level forbid.
- Only dedicated FFI modules may use `#![allow(unsafe_code)]`.
- Every unsafe block must have a directly preceding `// SAFETY:` comment explaining the
  invariant being upheld.
- Every public `unsafe fn` must have a `# Safety` rustdoc section that states caller
  obligations.
- Do not use raw pointers, `transmute`, `MaybeUninit`, manual `Send`/`Sync`, or unchecked
  indexing to silence the borrow checker.
- Unsafe code requires `unsafe-checker` review and focused tests that exercise the safe API
  around the unsafe boundary.

## 2. FFI and Generated Bindings Contract

FFI is a transition and oracle mechanism. It must not leak into ordinary Rust domain code.

- Raw generated bindings live under `ffi::sys`.
- Safe wrappers live under `ffi` or a feature-specific bridge module.
- Generated files must be reproducible, allowlisted, and regenerated by documented commands.
  Never manually edit generated bindings.
- C++ exceptions must not cross the Rust FFI boundary. Catch exceptions on the C++ side or
  expose status/message APIs that Rust converts into `Result` plus message records.
- Every handle must document ownership: borrowed, uniquely owned, shared upstream global, or
  transferred.
- `Drop` implementations must release owned handles exactly once and must tolerate partially
  initialized construction failure.
- FFI wrappers must convert C strings at the boundary and must reject interior NULs when
  constructing C-compatible strings.
- Safe wrappers must never expose raw C++ references, raw GMP/MPFR internals, or pointers
  whose lifetime is controlled outside Rust.
- Access to upstream global `calculator`/`CALCULATOR` state must be serialized and must save
  and restore mutable settings around each oracle/fallback call.

## 3. Numeric Backend Contract

The `Number` port must preserve arbitrary precision, exactness, approximation flags,
intervals, complex values, infinities, NaN, and uncertainty.

- Do not use `f64` or `i128` as semantic shortcuts for arbitrary precision arithmetic.
  Narrow primitive conversions are allowed only for parsing helpers, display helpers, or
  tested interop boundaries.
- Deep clone semantics must match upstream value ownership. Cloning a Rust `Number` must not
  create hidden aliasing of mutable numeric internals.
- Rational values must normalize signs and reduce by GCD.
- Precision is part of the calculation context and must propagate through float operations.
- Interval arithmetic must use outward rounding and must preserve open/closed bound,
  infinity, and undefined-bound behavior.
- Complex values must preserve exact/approximate state independently for real and imaginary
  parts.
- Uncertainty must be modeled explicitly. Do not collapse uncertainty into a plain interval
  unless the task documents that upstream-visible behavior is identical and tests prove it.
- Safe APIs must keep invalid states unrepresentable where practical. If a transitional state
  is needed, keep it private and validate before exposing it.

## 4. MathStructure and Domain Model Invariants

Upstream `MathStructure` uses mutable raw-pointer trees. Rust must not emulate that memory
model directly.

- Use enum-backed domain types for expression nodes.
- Parent nodes own children with `Box`, `Vec`, arena IDs, or another explicit owner. Avoid
  reference cycles.
- Child order, operator arity, associativity, and precedence must be encoded and tested.
- Definition references to variables, functions, units, prefixes, and datasets should use
  stable IDs or registry handles rather than raw pointer identity.
- Mutation APIs must recompute cached precision, approximation, interval, and unit metadata
  before returning a public value.
- Deep clones must duplicate expression structure without sharing mutable children.
- Formatting must be treated as user-visible behavior, not debug output.

## 5. Calculator State and Concurrency

Rust APIs should use explicit session ownership instead of upstream-style hidden globals.

- Model calculator state as `CalculatorContext` or an equivalent explicit session object.
- Keep precision, angle unit, base settings, print options, parse options, active
  definitions, messages, variables, assumptions, and data directories inside that context.
- Do not introduce global mutable Rust state for normal evaluation.
- No type should implement or derive `Send` or `Sync` unless thread-safety has been audited.
- C++ fallback access is thread-confined or guarded by a mutex. Do not hold locks across
  callbacks, user hooks, or reentrant FFI calls.
- Cancellation and abort support should be cooperative where possible. Worker resources must
  be joined or released in `Drop`.
- Tests that depend on locale, timezone, data directories, or global options must set those
  inputs explicitly.

## 6. Error and Message Compatibility

Upstream distinguishes fatal calculation failures from non-fatal warnings and queued
messages. Rust must preserve that distinction.

- Use `Result<T, E>` for fatal control flow.
- Preserve non-fatal warnings, messages, categories, stages, and ordering in calculator
  state.
- Error types may own `String`. Do not force all errors to be `Copy` if that loses upstream
  text or structured context.
- Parser and evaluator errors must not panic on runtime input.
- Diagnostics shown by CLI tests are part of compatibility and require oracle coverage.
- When a Rust error intentionally uses a different internal enum, document the upstream
  message behavior being preserved.

## 7. String, Unicode, and Locale Semantics

All pure Rust logic should use UTF-8 `String` and `str`, but upstream behavior includes
locale conversion, Unicode toggles, and platform-dependent wide strings.

- Track byte spans and character positions separately when diagnostics or cursor positions
  are user-visible.
- Do not assume `std::wstring` is always UTF-32. Treat wide-string width as a platform FFI
  detail.
- Convert C strings with `CStr` at the boundary and reject invalid UTF-8 unless a task
  explicitly implements locale-byte compatibility.
- Unicode case folding, string length, symbol display, and ASCII fallback behavior must be
  tested against `strings.batch` and focused fixtures.
- Interior NUL handling must be explicit for parser input, data files, and FFI calls.
- Locale-sensitive tests must pin locale inputs or record platform-specific deviations.

## 8. Definition Data and Provenance

Definition data is part of the product, not incidental test data.

- XML and JSON loaders must record source file, upstream version, and refresh path.
- Copied, generated, or transformed data must have bounded size and provenance.
- Unknown XML tags or missing optional fields must produce recoverable loader diagnostics,
  not panics.
- Definition registries must support lookup, aliasing, categories, descriptions, hidden
  items, and user overrides as upstream exposes them.
- Currency/rate loading must document offline behavior and refresh rules.

## 9. Build and Feature Parity

Hybrid builds must not hide unsupported upstream features.

- Map Rust Cargo features and `build.rs` behavior to upstream configure features.
- Track dependencies for GMP, MPFR, libxml2, pthread/threading, libcurl, ICU/localization,
  and platform C++ runtime behavior.
- Any unsupported upstream configure feature must be recorded in the compatibility inventory.
- Do not add dependencies with wildcard versions or unreviewed licenses.
- Generated code and vendored data must be reproducible in CI.

## 10. Review Gate

Before a porting task is complete:

- `code-review-context` must be able to identify the upstream files and fixtures used.
- `code-review-testing` must find tests for every user-visible behavior changed.
- `code-review-breaking-changes` is required for public API differences.
- `code-review-change-size` must confirm the change stayed within XS/S/M scope.
- `unsafe-checker` is required for FFI, raw pointers, generated bindings, manual
  `Send`/`Sync`, or any unsafe block.

If review evidence is missing, the task remains incomplete even if local tests pass.
